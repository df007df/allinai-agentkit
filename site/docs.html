allinai-agentkit 文档

连接业务系统与本地 AI Agent，统一派发任务并观察执行过程。 先了解功能与使用场景，再按快速开始运行；CLI、应用集成和架构细节可按需查阅。当前版本：v0.6.1。

1 项目做什么

allinai-agentkit 用来连接业务系统与本地 AI Agent，让你从一个入口派发任务，在指定机器上调用 Codex、Claude、Pi 或 zcode 执行，并集中查看运行状态、执行过程和结果。

它适合把 AI Agent 接入现有产品、内部工具或日常开发流程：从管理台让开发机检查代码项目，通过 Issue 安排 Agent 排查问题，或向多台执行机器分发统一的技能插件。

  • Hub 是任务派发和管理入口，可以启动自带的 Web 控制台，也可以作为 SDK 嵌入应用。
  • Client 常驻在执行机器上，连接 Hub，调用本机已安装的平台 Agent，并回传执行信息。

先使用官方控制台跑通任务，再根据业务需要接入自己的应用。平台 Agent 需在执行机器上单独安装并完成账号授权。

2 主要功能

按七组功能了解使用场景、解决的问题与提供的方案。每组的操作与实现参考可按需展开。

2.1 连接执行机器，统一派发多平台任务

使用场景： 你的内部平台、桌面应用或管理台需要发起代码修改、问题排查、文档整理等任务，并指定由哪台机器、哪种 Agent 执行。

解决问题： 不同 Agent 有不同的启动方式；业务系统还需要处理执行机器接入、任务传递和状态回传。每接入一个平台，都重复建设这些流程会增加维护成本。

提供方案： 由 Hub 管理接入的 Client，通过同一个任务入口选择执行机器和平台，Client 负责调用对应的本机 Agent。

  • 支持 Codex、Claude、Pi 和 zcode，沿用各平台在执行机器上的安装与账号配置。
  • Client 上报可用平台和已注册项目，控制台据此提供执行选项。
  • 可以直接使用自带的 Web 控制台派发任务，也可以通过 Hub SDK 接入自己的业务流程。

例如，管理台提交“检查 web 项目的登录逻辑”，选择开发机、Codex 和 web 项目后，由该机器上的 Codex 处理。

执行平台与事件适配参考

Client 调用本机 CLI 的非交互执行模式，例如 codex exec --json、claude -p --output-format stream-json 和 pi -p --mode json。doctor 探测本机命令是否存在；平台安装、账号与模型配置由各平台管理。

平台输出由适配器整理成统一事件后上报，详见事件模型。平台的工具确认接入与默认权限模式见人工确认参考。

2.2 常驻运行与连接恢复

使用场景： 执行机器需要持续接收任务，网络偶尔中断，或者你希望登录电脑后 Client 自动启动。

解决问题： 手工启动命令难以维持长期连接；连接断开后，中心容易丢失执行进度，重复投递也可能导致同一条任务被再次启动。

提供方案： Client 以常驻进程运行，维护连接和本地执行状态，连接恢复后补报尚未确认的事件。

  • 自动注册、发送心跳、断线重连，让 Hub 持续了解机器的在线状态。
  • 本地保存执行状态与待上报事件，对重复命令进行去重。
  • 可限制同时执行的任务数量，默认一次执行一个任务。
  • 支持注册为 macOS 或 Linux 用户级服务，在登录后自动启动；提供状态查询、重启、日志和自检命令。

连接恢复负责恢复通信和事件上报；正在执行的 Agent 会话如何恢复，取决于对应平台的能力。

常驻进程、状态保存与服务管理参考

Client 通过 WebSocket 维护连接，执行状态保存在 ClientStateStore，尚未确认的事件保存在本地后重投递。Hub 确认事件连续水位，Client 据此清理已确认记录。

maxConcurrentRuns 默认值为 1。可用 proxy 设置执行平台的 HTTP/HTTPS 代理。进程重启后的事件补报与平台会话恢复是分别处理的两件事。

install 注册 macOS launchd 或 Linux systemd 用户级服务，使 Client 随登录启动。日常使用 status、logs -f、doctor 和 restart 查询状态、排查环境和重启服务。

2.3 集中观察执行过程，保留排查依据

使用场景： 任务已经发出，你需要判断它是否开始、当前在做什么、是否等待人工确认，以及最终成功还是失败。

解决问题： 只看到“任务已提交”不足以判断执行情况；去每台机器翻终端输出，也难以把任务、平台会话和本地日志对应起来。

提供方案： Web 控制台集中展示 Client 状态和执行事件，Client 为每次执行保留独立的会话记录。

  • 实时查看 Client 的在线状态、可用平台、项目和插件信息。
  • 在执行列表与详情中查看状态变化、事件时间线，以及平台提供的会话标识。
  • 在同一个控制台处理待审批事项，并继续观察后续执行状态。
  • 本地保存会话事件、终态摘要和运行日志，方便按同一次执行排查问题。

官方控制台持久保存授权凭据与 Issues；执行事件的长期保存方式可在嵌入 Hub 时通过存储接口自行实现。

会话记录、日志与存储参考

每次执行保存 events.jsonl 状态时间线和 session.json 终态摘要。Client 的滚动运行日志位于 ~/.allinai/agent/logs/agent.log，使用 allinai-agentkit logs -f 跟随查看；日志按原文写入。

官方 Web 控制台将授权与 Issues 分别保存到 tokens.db 和 issues.db，默认 Hub 执行事件保存在内存中。需要跨 Hub 重启查询执行历史时，接入自己的 HubStore 与查询接口，见存储集成示例。

2.4 按项目选择工作目录

使用场景： 一台机器上有多个代码仓库，希望任务进入正确的项目目录；临时任务则需要独立的工作空间。

解决问题： 仅传一段提示词，Agent 未必知道应操作哪个项目。把工作目录和会话记录混在一起，也会让项目文件与运行记录难以管理。

提供方案： 在 Client 本地登记项目名称与目录，派发任务时按名称选择项目。

  • 已登记项目在其真实目录中执行，适合检查代码、修改文件、运行项目命令。
  • 未选择已登记项目时，使用按执行划分的临时目录，适合一次性任务。
  • 会话记录保存在 Client 的数据目录中，与项目文件分开管理。
  • 项目清单同步到控制台；本地新增或修改项目后，下一次任务即可读取新配置。

例如，在执行机器上登记 web 和 api 两个项目，控制台发起任务时即可选择对应项目。Hub 按项目名称选择本地登记的目录。

项目注册、目录与配置刷新参考 
allinai-agentkit project --name web --path /absolute/path/to/your-project
allinai-agentkit projects
allinai-agentkit project --name web --remove

注册路径必须是绝对路径。任务通过 payload.project 选择本地项目名称，Client 在下一次任务时读取最新注册；控制台的项目下拉来自 Client 上报的清单。首次使用应先登记再启动 Client；运行中新增项目后，重新连接 Hub 可更新清单。用户服务可用 restart 重连，前台运行时重新启动 daemon。

  • 未选择已登记项目：工作目录为 ~/.allinai/agent/projects/default/runtime/<平台>/<executionId>/，会话记录在 ~/.allinai/agent/projects/default/sessions/<executionId>/。
  • 选择已登记项目：在登记目录中执行，会话记录在 ~/.allinai/agent/projects/<名称>-<dir>/sessions/<executionId>/。

2.5 统一管理插件与技能

使用场景： 一组技能需要分发给多台机器，或同时提供给 Codex、Claude、Pi 使用；部分机器还需要保留自己的插件。

解决问题： 手工复制技能容易造成版本不一致；更新时还可能覆盖本地修改，或者无法判断插件是否已成功安装到目标平台。

提供方案： 以 Git 仓库承载插件与技能，由 Hub 或 Client 登记，Client 同步后按插件声明和本机平台进行分发。

  • Hub 管理统一的插件清单，Client 也可以登记机器自有插件，两类登记分别维护。
  • 一个插件可以包含多个技能与平台入口，支持向已安装的 Codex、Claude、Pi 分发。
  • 控制台展示插件同步与平台分发状态，便于发现安装失败或版本差异。
  • 支持检查更新、指定版本与回退；遇到受版本控制的本地修改或领先提交时，暂停自动更新，由人选择覆盖或保留。
  • 内置系统插件提供 Client 操作说明、Issues 操作指引，以及支持平台的工具确认接入。

插件结构、各平台分发方式和冲突处理见插件专页。

插件登记与分发参考

中心在控制台登记 Git 地址与分支，通过 plugin.sync 下发期望清单；本地通过 plugins --action install --git-url URL --id ID 登记机器自有插件。Client 拉取仓库、检查变更，并向插件声明且本机已安装的平台分发。

仓库布局、更新冲突、平台安装方式、移除与回退见插件与技能专页。

2.6 接入授权、本地策略与人工审批

使用场景： 新执行机器接入 Hub 时需要确认身份；部分任务希望先审批，再启动；Agent 执行中提出确认请求时，需要人参与决定。

解决问题： 机器接入、任务启动审批和运行中的工具确认属于不同环节，需要分别管理，并让人的决定能够回到执行端。

提供方案： Client 通过浏览器授权接入，运行前应用本地策略，支持的平台工具确认请求通过审批桥交给控制台处理。

  • 每个 Client 使用自己的身份与授权凭据，登录时在浏览器确认接入。
  • 本地可配置任务启动审批与插件来源规则，按执行机器分别维护。
  • 可开启任务启动前审批，控制台允许后才开始执行；默认配置为自动启动任务。
  • 对接入审批桥的 Codex、Claude、Pi 工具确认请求，可在控制台选择允许或拒绝，决定回传给等待中的请求。
授权、策略与审批配置参考

浏览器授权后签发与 clientId 对应的凭据，保存在本机 0600 文件中。嵌入 Hub 时由宿主提供 authorize 鉴权接口。

policy.requireRunApproval 默认是 false；设为 true 后，任务先进入 awaiting_approval，等待控制台允许或拒绝。插件同步可设置来源规则，能力调用使用对应的工作目录与权限策略。

运行中的工具确认由支持平台的 hooks 或扩展接入本地审批桥，决定经 Hub 回传给等待中的请求。接入范围、默认行为与回退规则见人工确认参考。

2.7 用 Issues 组织人与 Agent 的协作

使用场景： 一个问题需要先描述背景，再分配、讨论、执行和跟踪，例如让 Agent 排查缺陷，再由人确认结论与下一步。

解决问题： 单次提示词缺少持续的工作记录，讨论内容、执行过程和处理状态容易散落在不同位置，后续很难知道谁在处理、做到哪一步。

提供方案： 内置 Issues，把问题描述、评论、状态与关联执行放在一起，并支持在评论中通过 @Agent 发起处理。

  • 创建 Issue，维护标题、背景、优先级、负责人和处理状态。
  • 通过评论与回复补充事实、讨论方案，收件箱汇集分配、提及和状态变化等通知。
  • 在评论中提及已接入的 Agent，系统结合 Issue 内容和近期评论派发任务。
  • 为 Agent 提供读取 Issue、回复评论、更新状态的 CLI，让它能按任务要求把结论写回工作记录。
  • 同一 Issue 中同一 Agent 的执行尚未结束时，新的提及先合并等待；若 Issue 仍在处理中，本次执行成功结束后再处理后续内容。

例如，创建“登录后页面空白”，补充复现步骤并 @开发机 请求排查；Agent 收到带背景的任务，可读取完整讨论、回复发现并更新状态，人再据此继续确认。使用步骤见 Issues 协作。

Issue 提及、执行与回写参考

评论中提及已接入的 Agent 后，任务携带 Issue 描述、状态、优先级、近期讨论和触发评论，并附带读取完整 Issue、回复与更新状态的 CLI 指引。Agent 按指引回写结论，关联执行可在 Issue 中查询。

执行成功结束且 Issue 仍需处理时，再派发等待中的新提及。执行失败会留下失败记录，等待中的提及由后续人工跟进。已完成或已取消的 Issue 不再由新提及触发执行。

操作流程与命令见Issues 协作。Issue 提及任务使用 Client 的默认工作目录；需要在登记项目目录执行时，可从控制台的普通任务入口选择项目，再把结论回复到 Issue。

3 安装

环境要求：Node.js ≥ 22.18；插件同步需要本机 git。三种方式按需选择。

包部署位置与用途命令
@allin-ai/agentkit-hubHub 机器：SDK、Console、Issues 与预构建 Next.js 控制台allinai-agentkit-hub web
@allin-ai/agentkit-client执行机器：持久 Client、平台执行器、插件与本地控制面allinai-agentkit daemon

两个包没有相互的生产依赖。只接入现有 Hub 的机器安装 Client 即可；业务服务嵌入 Hub 使用 npm install @allin-ai/agentkit-hub。

3.1 npx 免安装

分别使用 npx 启动 Hub 控制台或 Client：

npx @allin-ai/agentkit-client --help
npx @allin-ai/agentkit-hub web

3.2 npm 全局安装

# Hub 机器
npm install -g @allin-ai/agentkit-hub
allinai-agentkit-hub --help

# 执行机器
npm install -g @allin-ai/agentkit-client
allinai-agentkit --help

Client 也可使用仓库提供的一键脚本（自动检查 Node 版本并验证安装）：

sh scripts/install.sh                 # 安装最新版 Client
sh scripts/install.sh 0.6.1           # 指定 Client 版本
sh scripts/install.sh --from-source   # 本仓库构建 + npm link Client（开发）

3.3 源码构建

git clone https://github.com/df007df/allinai-agentkit.git
cd allinai-agentkit
pnpm install && pnpm build

node bin/allinai-agentkit --help

3.4 从旧包迁移

npm uninstall -g @allin-ai/agentkit @allin-ai/agentkit-web
npm install -g @allin-ai/agentkit-client @allin-ai/agentkit-hub

将 Hub、Console、Issues 导入改为 @allin-ai/agentkit-hub/...，Client 导入改为 @allin-ai/agentkit-client/...。allinai-agentkit web 改为 allinai-agentkit-hub web；其他 Client 命令、v2 wire 协议与默认数据目录保持兼容。原 Web 包已并入 Hub 包。

数据目录：~/.allinai/agent（config.json、sqlite 状态库、日志、插件目录、 控制面 socket）。所有命令可用 --config-dir PATH 指向别的位置。

4 快速开始

先完成安装，并在执行机器上安装、登录至少一个支持的平台 Agent。以下步骤使用全局安装的命令；npx 用户换成对应包名，源码用户换成 node bin/...。

步骤一：启动 Hub 控制台（终端 A）

allinai-agentkit-hub web

打开 http://127.0.0.1:4317。Hub 控制台默认监听本机地址；跨机器接入时，使用 Client 可访问的 Hub 地址，并按部署方式设置监听地址或接入现有服务。

步骤二：安装后的 Client 授权（终端 B）

allinai-agentkit login --hub http://127.0.0.1:4317

命令打开浏览器授权页面，确认后保存该 Client 的凭据。可用 --name 开发机 设置控制台里的显示名。

步骤三：登记项目、启动 Client 并发起任务（终端 B）

需要处理已有仓库时，先登记项目，将示例路径换成真实的绝对路径；一次性任务可跳过项目登记。

allinai-agentkit project --name web --path /absolute/path/to/your-project
allinai-agentkit projects
allinai-agentkit daemon

保持终端运行。控制台随后显示在线 Client、可用平台和项目。选择机器、平台与 web 项目，输入任务，例如“检查登录流程，说明可能的问题和修改建议”，提交后观察状态、执行事件和结果。

需要人工确认时，在控制台允许或拒绝相关请求。每次执行的会话记录保存在 Client 数据目录中；持续跟进一个问题可使用下方的 Issues 流程。

4.1 接入授权与数据保存

每个 Client 使用自己的身份和凭据。浏览器确认接入后，官方控制台保存授权，重启后可以继续使用。嵌入 Hub 时，由应用提供自己的鉴权接口。

官方控制台默认在 ~/.allinai/agent 保存 tokens.db 和 issues.db；授权、Issue 状态与评论在重启后保留。可用绝对路径为 Hub 指定独立数据目录：

allinai-agentkit-hub web --config-dir /absolute/path/agentkit-hub

4.2 用 Issues 持续协作

  1. 在控制台创建 Issue，写清问题背景、复现步骤和希望获得的结论。
  2. 在评论中提及已接入的 Agent，请求它处理问题；系统将 Issue 内容和近期讨论随任务派发。
  3. 观察关联执行，Agent 可通过 CLI 读取完整讨论、回复发现，并按要求更新处理状态。
  4. 人查看结论，继续补充事实或确认完成。执行期间的新提及在成功结束后合并处理，失败时根据记录继续跟进。

完成授权的 Client 使用已保存的凭据读写 Issues：

allinai-agentkit issue list
allinai-agentkit issue show ISSUE-12 --json
allinai-agentkit issue comment ISSUE-12 --body "已完成核验，发现与验证结果如下……"
allinai-agentkit issue update ISSUE-12 --status in_review --priority P1
allinai-agentkit issue inbox

Client 全部子命令：allinai-agentkit <init|login|daemon|install|status|logs|sync|restart|uninstall|doctor|projects|project|plugins|issue|docs>。Hub 使用独立的 allinai-agentkit-hub web。

命令作用选项
init 初始化本地配置。适合无浏览器的服务器 / CI：可预置 token 直接完成配对 --hub URL* · --client ID · --token T
login 浏览器授权配对，保存 token；输出 authorizeUrl 并自动开浏览器。--name 为 client 起显示名（授权页与控制台 client 列表展示），clientId 由 client 本地生成并持久化 --hub URL* · --client ID · --name N · --no-browser
daemon 前台运行常驻 daemon：连接、注册、收任务、本地执行、事件回报 —
allinai-agentkit-hub web 启动本地 Console：Hub 与 web UI 同进程（Hub 包的独立命令） --port N（默认 4317，0 分配临时端口） · --host H（默认 127.0.0.1） · --config-dir PATH（绝对路径） · --dev（源码开发）
install 注册用户级系统服务（macOS launchd / Linux systemd），登录后自动启动 —
uninstall 移除用户级系统服务 —
restart 重启用户级系统服务（改配置后立即生效） —
status 经本地控制面查询 daemon 健康与运行状态（JSON 输出） —
logs 查看执行日志（滚动 JSONL，原样输出） -f 跟随新增
sync 触发本地持久工作的 flush；只处理本地状态，不接受 Hub 下发的命令 —
doctor 自检：git 是否可用、config 是否合法、是否已配对、各 runtime 安装探测 —
projects 列出已注册的项目工作目录 —
project 注册 / 移除项目目录，供 agent.run 按 project 名选取 --name N* · --path DIR（绝对路径） · --remove
plugins 列出已安装插件；--refresh 向 Hub 重新上报插件清单 --refresh
docs 输出完整 CLI 使用手册索引：默认 Markdown（人与 AI 均可读），--json 为同一份内容的结构化输出，AI agent 读完即可自行配置与执行 --json
issue show|list|comment|update|inbox 读取 Issues、评论、修改状态与优先级、读取当前 Client inbox；使用已保存的 Hub token --status · --priority · --body · --json（show）

全局选项：任一命令支持 --help；所有命令支持 --config-dir PATH 指定数据目录（默认 ~/.allinai/agent）。 标 * 的为必填。

6.1 将任务派发接入现有应用

6.4 Next.js 集成

Route Handler 拿不到 WebSocket 升级事件，所以走 custom server 挂 Hub； 页面用 Server Component 直接读 Store，列出 client 与在线状态。 

// 1) src/server/hub.ts —— 单例；dev 热更新下也保持同一实例

const g = globalThis as unknown as {
  hub?: ReturnType<typeof createMemoryHub>;
};
export const hub =
  g.hub ?? createMemoryHub({ authorize: myAuthorize }); // 你的鉴权

// 2) server.ts —— custom server，拿到底层 http.Server 才能挂 WS

import { hub } from "./src/server/hub";

// 3) src/app/agents/page.tsx —— 页面上列出 client 与状态

// src/server/store.ts —— HubStore 的数据库实现（六个方法）
import {
  createAgentHub, type HubStore, type StoredOffer,
} from "@allin-ai/agentkit-hub/hub";

export class MyDbHubStore implements HubStore<MyUser> {
  async registerClient(input) {
    // 幂等：同 principal+clientId 返回稳定 connectionKey；
    // 归属冲突（同 clientId 不同 principal）必须拒绝
  }
  async heartbeat(input) { /* UPDATE clients SET last_seen = now() */ }
  async listPendingOffers(input): Promise<StoredOffer[]> {
    /* 只返回该 principal 拥有、未确认的 offer，按持久投递顺序 */
  }
  async enqueueOffer(input): Promise<StoredOffer> {
    // 先落库再返回；按命令身份去重，connectionKey 与注册一致
  }
  async ingestEvents(input) {
    /* (executionId, eventSeq) 去重落库；只回报已持久化的连续
       水位；收到即退役 run offer，done/failed 等终态取消 offer */
  }
  async acknowledgePluginSync(input) { /* 记录插件确认水位 */ }

  // 页面查询：内存版的 listClients() 是 testkit 专属糖，
  // 换库后由你的 Store 自己暴露读方法，例如 listClientsFromDb()
}

// src/server/hub.ts —— 换个构造参数，其余（server.ts、页面）不变

  authorize: myAuthorize,
  store: new MyDbHubStore(),
});

7.1 wire 协议

Hub 与 client 之间只走 /protocol 定义的 v2 wire 消息： 连接握手（hello）、命令下行（agent.run / plugin.sync 等）、事件批次上行、 心跳、确认水位（ack）、插件同步确认、清单上报。全部消息有 encode*/parse* 编解码与严格类型，是两侧共享的唯一消息定义。

7.2 事件模型：平台事件如何收敛成协议事件

各 runtime SDK 的事件词汇互不相同（codex 是 ThreadEvent，claude 是 stream message）。agentkit 不把任何一家的事件原样上网，而是分三层收敛： 适配器先把 SDK 事件归一为 7 种 PlatformEvent（进程内）， supervisor 再把它们装进 9 种生命周期 ClientEvent 的信封里上报 Hub。两条正交维度：生命周期（type）回答「执行处于什么阶段」， 内容类型（eventType）回答「agent 此刻做了什么」。

第 1 层 · 平台 SDK 原生事件（daemon 进程内）
codex · ThreadEvent（8 种）
  • thread.started
  • turn.started
  • item.started
  • item.updated
  • item.completed
  • turn.completed {usage}
  • turn.failed {error}
  • error {message}

item 有 8 种：agent_message · reasoning · command_execution · file_change · mcp_tool_call · web_search · todo_list · error

claude · stream message
  • system/init
  • stream_event text_delta / thinking_delta
  • assistant text / thinking 块
  • user tool_result
  • result is_error / subtype
  • system 其他 subtype

pi / zcode 各自的原生事件同样进入第 2 层归一。

适配器归一 · mapCodexEvent / mapClaudeMessage
vendor 原名保留在 payload.vendorEventType，无损可查
第 2 层 · PlatformEvent（7 种内容公约数，进程内）
init会话初始化（thread_id） text_delta模型输出文本 thinking_delta推理 / 思考 tool命令 · 文件 · MCP · 搜索 vendor无精确对应物的杂项（仅本地调试） done / error终态信号
supervisor 装信封 · 状态机 + 去重 + 批量上行
done/error → 终态；其余 → progress + 顶层 eventType
第 3 层 · ClientEvent（9 种生命周期 × 5 种内容维度，wire 协议）
received running awaiting_approval progress× eventType: init · text_delta · thinking_delta · tool · vendor done failed cancelled rejected recovery_required 
{
  "executionId": "a746ecc6-…",
  "eventSeq": 4,
  "type": "progress",          // 维度一：生命周期（Hub 状态机、去重、重放都靠它）
  "eventType": "tool",         // 维度二：内容类型（仅 progress 携带）
  "occurredAt": "2026-09-23T22:41:50.102Z",
  "payload": {
    "vendorEventType": "item.completed",   // codex 原名，始终保留
    "item": { "id": "item_1", "type": "command_execution" }
  }
}

平台事件对照表

codex 原生claude 原生PlatformEventClientEvent（上报格式）
thread.started system/init init progress · eventType=init
item.completed × agent_message stream_event text_delta / assistant 文本 text_delta progress · eventType=text_delta
item.completed × reasoning thinking_delta / assistant thinking thinking_delta progress · eventType=thinking_delta
item.started/updated/completed × command_execution、file_change、mcp_tool_call、web_search、todo_list user × tool_result tool progress · eventType=tool
turn.started 等无对应物事件 其余 system subtype vendor 仅本地调试，不上报 Hub
turn.completed {usage} result（成功） done done
turn.failed / error result（is_error） error failed

为什么不直接透传平台事件：生命周期是 Hub 的公共契约（水位去重、断线重放、 offer 退休、执行分组都依赖 9 种稳定枚举）；内容公约数让 Console UI 对 tool / text_delta 编程一次、四个 runtime 全适用； payload 里的 vendorEventType 与原始 item 保证零信息损失—— 想看 codex 原名，展开 payload 即可。Console 时间线上每个事件显示为 progress·tool 这样的复合标签，两个维度一眼可读。

7.3 模块明细

每个模块一张 IDE 风格卡片：标签栏是 import 路径，正文是模块说明。

协议与入口

entry.ts
1import * as agentkit from "@allin-ai/agentkit-client";

Client 根入口汇总本地执行 API、协议、runtime、plugins、配置与凭据。Hub 根入口位于 @allin-ai/agentkit-hub，提供 Hub SDK 与协议；Console、Web 和 testkit 使用各自的子入口。

protocol.ts
1import { parseClientHello } from "@allin-ai/agentkit-client/protocol";

v2 wire 协议：AGENT_CLIENT_PROTOCOL_VERSION 常量与全部 encode*/parse* 编解码——hello、命令下行、事件批次上行、 确认水位、清单上报、插件同步确认。Hub 与 client 共用的唯一消息定义。 /wire 是它的兼容别名。

createAgentHub({ authorize, store })：Node HTTP/WebSocket Hub。 鉴权回调返回你的 principal，持久化走 HubStore 六方法端口 （注册、心跳、待投递查询、入队、事件落库、插件确认）， 包只做协议编排，不绑定任何数据库。offer() 派发命令到指定 client。

8 排障

  • 先跑 doctor：allinai-agentkit doctor 输出 git、config、配对状态与各 runtime 探测，多数环境问题一眼可见。
  • daemon 没起来：status 看健康与状态；前台跑一次 daemon 直接观察日志输出。
  • 执行没反应：logs -f 跟随执行日志（JSONL），确认命令是否到达、策略是否放行、runner 是否可用。
  • 提示未配对：检查 token 是否有效；使用易失内存 token 存储的嵌入式 Hub 在重启后需重新 login --hub ...。官方控制台默认持久化 token；生产环境检查宿主 authorize 实现。
  • runtime 缺失：doctor 报告里看各 runtime 的 installed/reason，安装对应平台 CLI 后重启 daemon。
  • 服务不生效：改配置后 restart；确认 install 输出的平台与 configDir 符合预期。

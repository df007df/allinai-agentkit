插件与技能

把一组技能作为插件统一维护，分发到执行机器上的 Codex、Claude、Pi，查看安装状态，并处理版本更新与本地修改。

插件是一个 Git 仓库，包含技能与平台入口清单。Hub 管理需要分发的插件清单，Client 拉取仓库并向本机支持的平台分发；机器也可以登记自己的插件。当前版本：v0.6.1。

插件管理与执行位于 @allin-ai/agentkit-client，中心控制台位于 @allin-ai/agentkit-hub。项目的其他能力见七组主要功能。

使用场景、问题与方案

给多台机器分发共享技能

使用场景：代码审查、排错或部署指引需要在多台执行机器、多个 Agent 平台上重复使用。

解决问题：手工复制技能容易遗漏更新，也难以确认每台机器和每个平台实际使用的版本。

提供方案：将相关技能放入一个 Git 插件，在 Hub 登记后向选中的 Client 下发；Client 根据插件声明与本机平台分发，控制台显示同步和安装结果。

保留机器专用的插件

使用场景：统一技能之外，某台开发机需要自己的工作流程或试验中的技能。

解决问题：机器自己的插件与中心管理的插件，需要分别维护登记与移除，避免中心清单更新时丢失本地登记。

提供方案：通过 Client CLI 登记机器自有插件，由本地维护增删；Hub 维护的清单按中心登记管理。日常建议使用不同插件 ID，同 ID 的优先级规则见下方参考。

更新技能并处理本地修改

使用场景：上游技能发布了新版本，但执行机器的插件仓库可能有自己的修改；新版本有问题时还需要回退。

解决问题：自动覆盖会丢失本地修改，更新前也需要知道版本差异与冲突原因。

提供方案：检查上游后同步版本；受版本控制的本地修改或领先提交会暂停自动更新，控制台提供覆盖或保留的选择。需要固定或回退版本时，指定目标 commit。

从登记到使用

  1. 准备包含技能和平台入口的 Git 插件仓库。
  2. 在 Hub 控制台登记并选择执行机器，或在 Client 本地登记专用插件。
  3. Client 同步仓库，向已安装且支持的 Agent 平台分发。
  4. 查看同步和平台分发状态，再发起需要这些技能的任务。
  5. 后续检查更新，遇到本地修改时决定处理方式，必要时回退版本。

插件结构与存放位置

插件仓库结构

my-plugin/                          ← 一个 Git 仓库
├── allinai-plugin.json             ← agentkit manifest（声明 skills）
├── skills/                         ← 顶层 skills/ 目录，供支持的平台加载
│   ├── code-review/
│   │   └── SKILL.md                ← name/description front-matter 必填
│   └── deploy-helper/
│       └── SKILL.md
├── .claude-plugin/marketplace.json ← claude 入口（可选；分发到 claude 需要）
├── .codex-plugin/plugin.json       ← codex 入口（可选；可声明自带 hooks）
└── package.json                    ← pi 入口（pi.skills 指向 skills/）

manifest 最小形态：{ "id": "my-plugin", "skills": ["skills/code-review", "skills/deploy-helper"] }。 技能遵循 Claude SKILL.md 格式（YAML front-matter 的 name: 小写 slug、description: 必填——Pi 等平台会跳过无描述的技能）。 一个插件放多少个技能都可以：相关技能可以放在同一插件内维护，随插件一起同步和分发。

目录布局（client 侧）

~/.allinai/agent/plugins/<id>/repo/   ← 唯一常驻 clone（单仓 checkout 模型）
                                      "active 目录"就是 repo working tree

更新 = fetch + checkout，从不重建目录——技能运行期写入的 untracked 文件（缓存等）天然存活。旧版本永远在 Git 历史里，checkout 回去即回滚。

操作与管理参考

登记（两个入口，互不覆盖）

入口操作所有权
中心登记 Console 插件面板添加（id + Git 地址 + 分支），经 plugin.sync 下发期望清单 origin: hub——由中心清单管理增删
本地登记 plugins --action install --git-url URL --id ID [--ref REF] origin: local——Hub 全量推送不会移除它，只有本地 remove 能卸

两个入口走同一条同步管线（syncOne()），登记后即刻同步激活并分发。 同 ID 冲突时中心下发的配置优先；client 重连时 Console 自动补推期望清单（离线编辑重连即达）。

同步与分叉裁决

每次同步（中心信号 / 重连拉平 / CLI 手动，无定时器）执行三分支对比：

  • 干净且落后 → 自动 fast-forward 到目标 commit；
  • untracked 新文件 → 不算分叉，照常更新（临时文件存活）；
  • tracked 改动 或 本地领先 commit → diverged：拒绝自动更新、上报待裁决。

diverged 后 Console 出两个裁决按钮：强制覆盖（checkout --force 到中心目标， 本地 commit 仍在历史可找回）或 保留本地（刷新基线等人工合并）。 也可用 plugins --action force --id ID [--commit SHA] 钉死任意 commit（即回滚通道）。

多平台分发

同步成功后按「插件期望平台 ∩ 本机已装平台」自动分发（探针 = which 命令存在性）：

平台方式升级语义
codexcodex plugin marketplace add + plugin add拷贝进 cache——每次同步重装，版本钉死在安装时刻
pipi install <repo>本地路径引用——仓库更新实时生效
claude运行时 --plugin-dir <repo>直连，无需安装

每个平台的分发结果（installed / removed / skipped / failed）持久化并随 inventory.report 上报，Console 插件行内以徽章展示（悬停看失败详情）。

移除与回滚

  • 中心登记的插件：从中心清单删条目 → 下次同步 deactivate（自动逐平台卸载）；
  • 本地登记的插件：plugins --action remove --id ID；
  • 本地 remove 对 hub 登记的插件会拒绝（防止下次推送又装回来）；
  • 回滚 = force --commit <旧sha>，单仓模型下任意历史版本一步切回。

执行中的人工确认

使用场景：Agent 执行任务时提出工具确认请求，需要人在控制台决定是否继续相关操作。

解决问题：确认请求产生在本地 Agent 中，而操作人员可能正在 Hub 控制台观察任务，需要将请求和决定对应起来。

提供方案：内置系统插件为 Codex、Claude、Pi 提供确认接入，通过本地审批桥把支持的请求展示到控制台，再把允许或拒绝决定回传到等待中的请求。

任务启动前审批由 Client 本地配置单独控制，默认自动启动；工具确认接入处理平台发出的确认请求。两者的使用说明见授权、策略与人工审批。

平台 hooks、审批桥与默认行为参考

当前适配的工具调用默认放行；接入的确认请求通过两段式审批桥登记并等待决定，人工明确拒绝时拦截相关操作。daemon 不在线、等待超时等情况的回退规则如下。

agent 请求执行需确认的工具（ask-user 时刻）
  → 平台 hooks（随 agentkit-system 插件进入受管项目）
  → 段1：POST 审批桥注册 → 桥签发 requestId 并弹卡
  → 段2：hook 携 requestId 挂等 → Console 人工 allow/deny
  → 决定经 respond_tool_approval 原路唤醒 hook
  → 人工拒绝才拦截，其余显式放行
  • 默认行为与回退：拦截只发生在人工明确 deny 时；daemon 不在线、超时或无人工记录一律放行（claude 侧放行为显式回包——平台语义是 hook 空回复即自动拒绝）；
  • ask-user 时刻：claude = PermissionRequest 事件（平台准备请求授权时；bypassPermissions 会跳过该确认事件，因此 claude 运行采用默认权限模式、由 hook 回包实现放权）；codex = pre_tool_use 审批钩子（danger-full-access 沙箱不影响其触发）；pi = 扩展对执行/写类工具（bash/edit/write）的 tool_call 拦截；
  • 两段式闭环：requestId 把 Console 的卡片和挂起的 hook 一一对应，人工决定经现有 respond_tool_approval 通道回放——没有 requestId 转发就到不了 hook；
  • 插件作用域：hooks 随插件进入受管项目目录，只对受管会话生效——单独使用平台 CLI 的会话按该平台配置运行；
  • 三平台入口：claude = 插件 hooks/hooks.json（${CLAUDE_PLUGIN_ROOT}）；codex = 插件 manifest 的 hooks 组件（headless 路径自动托管信任）；pi = 包内 pi.extensions 扩展；
  • 不再有用户级安装：hooks 不是全局开关，跟插件走。

内置 agentkit-system 插件

Client 启动时自动准备系统插件，用于帮助 Agent 操作 Client 和参与工作流程，主要内容：

  • client-control 技能：从 CLI 手册生成，教 agent 操作宿主—— 装插件/skill、查 daemon 状态与日志、项目注册、数据目录布局；
  • Issues 技能：帮助 Agent 读取 Issue 背景、回复处理结论与更新状态；
  • 三平台 tool ask-user hooks：上一节的上报载体，随本插件的分发自动进入受管项目；
  • 幂等升级：内容随 Client 包版本更新，重复启动时保持一致。

控制台管理

Console 插件面板提供全生命周期操作：

  • 查看：每插件的启用、失败或待处理本地修改状态、当前 commit、每平台分发徽章；
  • 登记：表单添加（id + Git 地址 + 可选分支），下发到选中 client；
  • 裁决：diverged 插件两按钮（强制覆盖 / 保留本地）；
  • 移除 / 重推：删条目或把整份期望清单重新下发（client 离线时用）。

CLI 速查

allinai-agentkit plugins                                   # 列出已装插件（含每平台分发摘要）
allinai-agentkit plugins --refresh                         # 重新上报 Hub
allinai-agentkit plugins --action install \
  --git-url https://github.com/me/skills.git --id my-skills  # 本地登记（机器自有）
allinai-agentkit plugins --action remove --id my-skills      # 卸载本地登记
allinai-agentkit plugins --action check                     # 对比上游（不动本地）
allinai-agentkit plugins --action update                    # 拉取更新（无需 Hub 在线，仍需访问 Git 仓库）
allinai-agentkit plugins --action force --id my-skills \
  --commit <sha>                                             # 钉死/回滚到任意 commit

编程接入：@allin-ai/agentkit-client/plugins 的 PluginManager（sync / check / forceTo / remove）， 中心侧 hub.syncPlugins() 与 Console HTTP 端点 GET/POST /_agentkit/console/plugins。完整 API 见 完整文档。
